# 系统化调试

## 目标

在修改代码前确认可复现的真实根因，并以最小修复恢复预期行为。

## 开始前

1. 读取根 `AGENTS.md`、项目地图、验证规则和受影响端的 Rule。
2. 获取完整错误、输入、环境、时间点和最小复现步骤。
3. 检查 Git 状态，确认现有修改是否参与故障或需要保留。

## 流程

1. 稳定复现，记录实际结果与预期结果。
2. 还原数据流：对 API 问题追踪客户端调用、FastAPI 路由、Schema、Service、ORM/外部服务和响应转换。
3. 确定失败的最窄层级：环境/配置、网络、认证、契约、业务逻辑、持久化、缓存/向量库或 UI 状态。
4. 提出可被证伪的假设，为每个假设指定一个最小观察或实验。
5. 每次只验证一个假设，保存证据后再转向下一个。
6. 确认根因后先补一个能重现的自动化回归；现有基础设施无法支持时，记录精确手工回归步骤。
7. 实施最小修复，不同时做无关重构。
8. 运行定向回归、受影响端验证和必要的扩大验证。

## Elearning 专项检查

- Web API 异常：检查 `/Elearning/api/v1`、Vite 代理和局部硬编码 URL 是否一致。
- 小程序请求异常：检查 `USE_CLOUDBASE`、`BASE_URL`、Token 持久化和微信合法域名配置。
- 后端启动异常：区分 Python 依赖、`.env`、MySQL、Redis、Milvus 和外部 API 失败；不要一次启动全部服务来猜测。
- AI/文档/媒体链路：从最小不含外部调用的探针开始，再逐层验证凭据、请求、响应解析、持久化和下游消费。

## 停止条件

- 需要真实生产凭据、支付、部署或生产数据变更。
- 需要删除/覆盖上传文件、数据库数据或用户现有修改。
- 多种产品行为都合理，而选择会显著改变用户体验或数据语义。

## 禁止

- 未确认根因前增加兜底、重试、宽泛 `except` 或默认值来隐藏故障。
- 同时改变多个变量后仅根据“看起来好了”宣称修复。
- 为了便于调试而记录密钥、Token、完整个人数据或文件原文。

## 交付

说明复现、根因、修复、验证命令/结果、未覆盖范围和残余风险。
