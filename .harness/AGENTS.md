# AGENTS.md

## 语言

默认使用简体中文。命令、路径、代码标识符和外部协议名称保持原文。

## Harness 入口

根目录 [AGENTS.md](../AGENTS.md) 将项目任务引到本文件。以下代码路径均相对于仓库根目录。除纯解释、单文件机械修改等简单任务外，开始前读取 [Application Owner](.agent/application-owner.md) 和 [项目地图](wiki/项目地图.md)。

先以当前代码、配置和测试结果为事实，再参考历史文档。规划、原型和 Change Audit 不得覆盖当前运行事实。

## 从请求确定交付物

1. 按用户指定的阶段、路径和格式交付。解释、讨论和评审默认在会话中完成。明确要求输出开发方案时，默认保存到 `docs/plans/`，包括“先给开发方案”的请求。“先给方案”限定本轮为方案阶段。用户要求仅在会话中回复时，直接在会话中交付。
2. 明确要求编写、实现、更新或沉淀项目成果时，直接创建或更新相应文件。先查找同一主题的已有文件，沿用其命名和格式。新建文字文档默认用 Markdown。
3. 一次请求包含多个成果时分别交付。例如“写一份 PRD，再做可预览原型”，分别保存 PRD 和可打开的原型，并给出两个链接。

| 请求或任务 | 读取与写入规则 |
|---|---|
| 编写 PRD、验收标准、设计稿或原型 | 先查 [产品资料说明](../product/README.md) 和已有需求。PRD 与验收标准写入 `product/prd/`，设计稿与原型写入 `product/design/`。 |
| 记录需求变更或产品决策 | 写入 `product/changes/`，说明变更内容和验收影响，链接相关 PRD。要求同步修改原需求时一并更新。 |
| 编写开发方案 | 按 [开发方案归档规则](../docs/plans/README.md) 选择 `docs/plans/` 下的分类，先查找同一事项的方案，优先更新已有文件，交付时给出路径。 |
| 查询或沉淀项目事实 | 从项目地图定位代码、配置或测试并核实。查询在会话中回答。明确要求整理进 Wiki，或本次实施使已有条目失效时，更新 `.harness/wiki/` 对应条目。新建专题页时从项目地图链接。 |
| 维护长期工程约束或角色职责 | 先查对应的 `.harness/rules/` 或 `.harness/.agent/` 文件。已有规则可直接引用。需要新增或修订约束时更新专项规则，角色分工写入角色文件，全仓触发条件和入口写在本文件。 |
| 编写启动说明、操作手册、验收指南 | 快速启动和导航写入根 [README](../README.md)，完整指南写入 `docs/`。README 和 Wiki 可链接同一份指南。 |
| 实现功能或维护工具 | Web 源码写入 `client/src/`，微信小程序写入 `client/miniprogram/`，后端、数据库和云函数分别归入 `server/` 对应模块。仓库级工具写入根 `scripts/`，服务端专用工具写入 `server/scripts/`，Harness 检查与验证工具写入 `.harness/scripts/`。 |

## 按影响范围加载规则

- Web 源码、Web 测试及 `client/vite.config.ts`、`client/package.json` 等构建配置，读取 [前端规则](rules/frontend.md)。
- FastAPI、Worker、数据库和服务端部署配置，读取 [后端规则](rules/backend.md)。
- `client/miniprogram/**` 或 `server/cloudfunctions/**`，读取 [小程序与云函数规则](rules/miniprogram.md)。
- 公开接口或其调用方发生变化，追加读取 [HTTP API 规则](rules/http-api.md)。涉及凭据、认证、支付、上传或外部服务，追加读取 [安全规则](rules/security.md)。
- 所有代码修改读取 [项目边界](rules/project-boundaries.md)、[架构规则](rules/architecture.md) 和 [验证规则](rules/verification.md)。跨端任务组合使用受影响端的规则。

## 项目 Skill 调用

用户点名项目 Skill，或任务符合下表触发条件时，打开对应的 `SKILL.md`，按当前请求执行适用步骤。

| 触发条件 | 入口 | 完成证据 |
|---|---|---|
| 启动报错、测试失败、实际行为偏离预期 | [系统化调试](skill/systematic-debugging/SKILL.md) | 诊断给出失败环节和依据。要求修复时，交付修改和定向复验结果。 |

用户要求沉淀可复用的操作流程时，先检查现有项目 Skill 的覆盖范围。更新已有 Skill，或在 `.harness/skill/<name>/SKILL.md` 创建流程，并在上表登记触发条件、相对链接和完成证据。会话中可用的外部 Skill 按任务选用，项目 Skill 表只登记本仓库维护的流程。

## 工作原则

1. 先写清目标、非目标、成功标准和关键假设。
2. 只加载与任务相关的最少规则，不机械读取旧平台规则全集。
3. 不回退、覆盖或清理用户已有的未提交修改。
4. 不做与目标无关的业务重构，不把原型或设计导出代码当成生产真源。
5. 修改接口时同时检查后端、Web 管理端和小程序调用方。
6. 完成前运行与改动范围匹配的统一验证命令；没有验证证据不得声称通过。
7. 无法运行的验证必须说明原因、未覆盖范围和风险。

## 安全与破坏性操作

- 禁止提交 `.env`、访问密钥、Token、数据库口令、微信密钥或真实用户数据。
- 删除数据、执行迁移、清理上传目录、覆盖生成物、重写 Git 历史或操作生产环境前，必须确认精确目标并取得用户授权。
- `server/database/alembic/versions/**` 中已应用迁移禁止原地改写；需要新建迁移。
- 不默认使用 `--no-verify`、`git reset --hard` 或其他绕过治理/破坏性命令。

## Change Audit

涉及既有需求或历史决策时，先按主题查找已有 Audit。新功能、跨模块重构、API 契约、数据库、认证/权限、AI 链路、生产配置变更及重要架构决策，按 [Audit 约定](changes/README.md) 和 [模板](changes/_template/summary.md) 在 `.harness/changes/<topic>-YYYYMMDD/summary.md` 记录实施决策、验证与风险。同一需求继续更新原记录，有对应产品变更时互相链接。小型文案或局部样式修改通常不需要 Audit。

## 交付

交付项目文件时提供可打开的链接。工程改动说明修改内容、验证命令与结果、跳过项和残余风险；涉及 Audit 时同时给出 Audit-ID 和路径。
